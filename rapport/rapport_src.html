Exercice 4 – Sécurité

Faille principale : l'injection SQL. Les méthodes précédentes construisent la requête par concaténation de chaînes avec des valeurs venant de l'utilisateur. Le SGBD ne fait aucune différence entre le code SQL écrit par le développeur et les données saisies : un utilisateur peut donc saisir du SQL qui sera exécuté.

Démonstration (dans une transaction annulée par un rollback pour ne pas abîmer la base) :

  • en saisissant 7369 OR 1=1 comme numéro d'employé, la requête devient UPDATE emp SET deptno = 40 WHERE empno = 7369 OR 1=1 : les 14 employés sont déplacés au lieu d'un seul ;
  • en saisissant x' OR '1'='1 comme nom, la condition du WHERE est toujours vraie et on récupère toute la table (contournement d'une authentification, fuite de données comme les salaires) ;
  • pour displayTable(tableName), on pourrait même passer emp; DROP TABLE emp.
[[method part1-jdbc/src/fr/isep/tp3/jdbc/Main.java|public static void sqlInjectionDemo(]] [[img ex4 | l'injection modifie 14 lignes au lieu d'une et renvoie tous les salaires]]

Autres inconvénients de cette méthode « native » :

  • Performance : avec un Statement, la requête est ré-analysée et re-planifiée par le SGBD à chaque exécution ;
  • Robustesse : une valeur contenant une apostrophe (ex. O'Neil) casse la requête, il faut tout échapper à la main ;
  • Pas de typage : les erreurs (nom de colonne, type) n'apparaissent qu'à l'exécution ;
  • Gestion manuelle des ressources : Connection, Statement, ResultSet à fermer, sinon fuite de connexions et saturation du serveur ;
  • Coût de la connexion : une connexion ouverte à chaque appel coûte cher (cf. partie IV) ;
  • le SQL est mélangé au code métier et le mapping ligne → objet est entièrement manuel (cf. exercice 8).

Comme le rappelle l'énoncé, la validation doit se faire côté serveur : un contrôle en JavaScript côté client se contourne facilement.

Exercice 5 – moveDepartment avec PreparedStatement

La requête est écrite avec des ? et les valeurs sont passées avec setInt. Le driver envoie la requête et les paramètres séparément au serveur : une valeur ne peut jamais être interprétée comme du SQL. Ici la saisie est lue comme une chaîne (pour pouvoir tenter l'injection) puis convertie en entier : une saisie non numérique est refusée avant même d'atteindre la base. J'utilise aussi un try-with-resources qui ferme automatiquement le PreparedStatement.

[[method part1-jdbc/src/fr/isep/tp3/jdbc/Main.java|public static void moveDepartmentPrepared(]] [[img ex5_attack | la même attaque « 7369 OR 1=1 » est refusée, la table n'est pas modifiée]] [[img ex5_ok | utilisation normale : SMITH (7369) revient dans le département 20]]

Exercice 6 – displayTable avec PreparedStatement

[[method part1-jdbc/src/fr/isep/tp3/jdbc/Main.java|public static void displayTablePrepared(]] [[img ex6 | « SELECT * FROM ? » provoque une erreur de syntaxe ; la version sécurisée fonctionne et refuse l'injection]]

Pourquoi ça ne marche pas ? Les paramètres ? d'une requête préparée ne peuvent remplacer que des valeurs (littéraux), jamais des identifiants (nom de table, de colonne) ni des mots-clés SQL. La requête est envoyée au serveur pour être analysée et planifiée avant que les valeurs soient connues : pour construire le plan d'exécution, PostgreSQL doit savoir quelle table lire. SELECT * FROM $1 n'est donc pas du SQL valide (d'où l'erreur syntax error at or near "$1", SQLState 42601). Et même si c'était accepté, setString produirait la chaîne littérale 'emp' et non l'identifiant emp.

Solution : vérifier le nom de table par liste blanche. J'interroge les métadonnées de la base (DatabaseMetaData.getTables) et je n'exécute la requête que si la table existe réellement.

3. Partie II – DAO

Exercice 8 – Inconvénients de JDBC tel qu'utilisé ci-dessus

  • Code de persistance dispersé dans le code métier : le SQL est écrit partout où on en a besoin (schéma « Before DAO »). Si une table change (colonne renommée, changement de SGBD), il faut modifier le code à de nombreux endroits ;
  • Pas d'objets métier : on manipule des ResultSet et des colonnes au lieu d'objets Emp / Dept ; le mapping relationnel → objet est refait à chaque requête ;
  • Beaucoup de code répétitif (« boilerplate ») : ouverture, try/catch/finally, fermeture des ressources, SQLException partout ;
  • Couplage fort au SGBD et au driver : impossible de changer de source de données (autre base, fichier, web service) sans réécrire le métier ;
  • Difficile à tester : on ne peut pas remplacer la base par un faux objet (mock) pour tester la logique métier ;
  • gestion manuelle des connexions (une par appel), des transactions et des relations entre tables (ex. le manager d'un employé).

Le pattern DAO répond à cela en isolant toute la persistance dans une couche dédiée : le métier ne manipule que des objets et des méthodes find / create / update / delete, sans savoir comment ni où les données sont stockées.

[[code part1-jdbc/src/fr/isep/tp3/dao/EmpDAO.java]] [[img ex11 | SMITH est reconstruit avec toute sa chaîne hiérarchique : SMITH → FORD → JONES → KING]]

Remarques / limites observées :

  • Chaque niveau de hiérarchie déclenche 2 requêtes (employé + département) : c'est le problème classique du « N+1 select ». Pour une liste d'employés il vaudrait mieux une jointure ou un cache des objets déjà chargés (ce que fait JPA avec son contexte de persistance) ;
  • si les données contenaient un cycle (A manager de B et B manager de A), la récursion serait infinie : un cache par identifiant règlerait aussi ce cas ;
  • getInt() renvoie 0 pour un NULL : sur la capture, comm=0 pour SMITH alors que la valeur est NULL en base. Utiliser Integer dans le bean permettrait de distinguer les deux (c'est ce que fait le générateur de la partie V).

Remarque : la deuxième version du contrôleur de l'énoncé utilise @Param("name") de org.springframework.data.repository.query. Cette annotation sert à nommer les paramètres des requêtes des repositories Spring Data, pas à lire un paramètre HTTP ; cela fonctionne uniquement parce que le nom de la variable Java est aussi name. J'ai gardé @RequestParam(value = "name", required = false), qui est l'annotation correcte.

III.4 – Création d'un objet via JPA + Swagger

Ajout de la méthode @PostMapping("/employees") qui appelle empRepository.save(emp). Au premier test, la création échoue :

[[img post_error | erreur 500 : la séquence hibernate_sequence n'existe pas]]

Explication : l'entité de l'énoncé porte @GeneratedValue sans stratégie, donc GenerationType.AUTO. Avec PostgreSQL, Hibernate 5 choisit alors une séquence nommée hibernate_sequence (select nextval('hibernate_sequence'))... qui n'existe pas dans notre schéma, puisque empno est une clé saisie manuellement (pas de SERIAL / IDENTITY). Correction : j'ai retiré @GeneratedValue ; l'empno est fourni par le client dans le JSON, comme dans la base d'origine. (Autre solution possible : créer une séquence et utiliser @GeneratedValue(strategy = GenerationType.SEQUENCE) avec @SequenceGenerator.)

Pour Swagger, Springfox 2.9.2 n'est pas compatible avec le nouveau moteur de correspondance d'URL de Spring Boot 2.6+ ; il faut ajouter spring.mvc.pathmatch.matching-strategy: ant_path_matcher dans application.yml, sinon l'application ne démarre pas.

5. Partie IV – Pool de connexions (bonus)

IV.1 – Pool de connexions « fait main »

Au démarrage, le pool ouvre N connexions via une DataSource (PGSimpleDataSource) au lieu du DriverManager et les range dans une ArrayBlockingQueue. Un client prend une connexion avec getConnection() et la rend avec release() au lieu de la fermer. La BlockingQueue est thread-safe : si toutes les connexions sont prises, le thread appelant attend qu'une connexion soit rendue, ce qui borne le nombre de connexions ouvertes sur le serveur.

[[code part1-jdbc/src/fr/isep/tp3/pool/ConnectionPool.java]]

IV.2 – BoneCP

Grâce à l'interface ConnectionProvider, passer du pool maison à BoneCP ne change que quelques lignes : c'est l'intérêt d'avoir isolé l'obtention des connexions. Avec BoneCP, close() ne ferme pas la connexion mais la rend au pool.

[[code part1-jdbc/src/fr/isep/tp3/pool/PoolMain.java]]

Mesures

Test : 500 requêtes SELECT exécutées par 10 threads en parallèle.

[[img pool | comparaison sans pool / pool maison / BoneCP]]

Sans pool, les 500 requêtes prennent environ 5,2 s ; avec un pool, environ 50 à 75 ms, soit un facteur d'environ 100. Presque tout le temps est passé à ouvrir les connexions (connexion TCP, création d'un processus côté PostgreSQL, authentification SCRAM-SHA-256 volontairement coûteuse), et non à exécuter la requête elle-même. Le pool paie ce coût une seule fois au démarrage. On voit aussi que BoneCP n'a créé que 7 connexions pour servir les 10 threads.

BoneCP n'est plus maintenu : son auteur conseille lui-même HikariCP, qui est justement le pool par défaut de Spring Boot (cf. logs de la partie III) et qui se règle dans application.yml (spring.datasource.hikari.maximum-pool-size, etc.).

7. Conclusion

Ce TP montre l'évolution de l'accès aux données en Java :

  1. JDBC brut : contrôle total mais beaucoup de code, et des risques réels (injection SQL, fuites de connexions). Le PreparedStatement est indispensable dès qu'une valeur vient de l'utilisateur, et un identifiant (nom de table) doit être validé par liste blanche ;
  2. DAO + Factory : la persistance est isolée du métier, qui manipule des objets ; mais le mapping (notamment les relations comme le manager) reste à écrire et à optimiser à la main ;
  3. Spring Boot + JPA : le framework fournit le DAO (repository), le mapping, le pool de connexions (HikariCP) et l'exposition REST, avec très peu de code. Il faut néanmoins comprendre ce qu'il fait pour corriger les problèmes rencontrés (séquence hibernate_sequence, compatibilité des versions, getters manquants) ;
  4. le pool de connexions divise le temps de réponse par environ 100 dans notre test, ce qui justifie son usage systématique côté serveur.
